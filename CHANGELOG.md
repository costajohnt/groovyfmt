## Unreleased

## 0.13.0 (2026-11-13)

### Added

- `groovyfmt --import-codenarc <FILE>...` prints the `[lint]` table of a `.groovyfmt.toml` that carries over a CodeNarc configuration: ruleset XML, a Groovy ruleset, `codenarc.properties`, or npm-groovy-lint's `.groovylintrc.json`. Each groovyfmt rule named after a CodeNarc rule comes out on or off as the configuration says, and the rules it can't carry over follow as comments: those groovyfmt has no equivalent for yet, those that need type information, the formatting rules the formatter covers (with the settings that cover them), the properties it ignores, and anything it couldn't interpret. Nothing in a configuration is run and nothing is fetched. The rulesets CodeNarc bundles and npm-groovy-lint's presets come from tables generated from CodeNarc 4.0.0 and npm-groovy-lint 19.0.1 (`scripts/codenarc-data.py`), and other referenced rulesets are read only from inside the configuration's directory. `-v` shows where each rule's setting comes from. On the 37 CodeNarc configurations in about 120 open source projects it reads all of them. ([migrating from CodeNarc](docs/lint.md#migrating-from-codenarc))
- Ten lint rules from CodeNarc's `basic`, `unnecessary` and `naming` rulesets, the ones most often enabled in those 37 configurations that a single file's syntax decides: `UnnecessaryInstanceOfCheck` (`!x instanceof T`), on by default, since all 15 places it reports in those projects are bugs; and, off by default, `BigDecimalInstantiation`, `BitwiseOperatorInConditional`, `ClassNameSameAsFilename`, `DoubleNegative`, `EmptySynchronizedStatement`, `ForLoopShouldBeWhileLoop`, `IntegerGetInteger`, `RandomDoubleCoercedToZero` and `UnnecessaryModOne`, which on the same code report mostly what is written that way on purpose (bit-flag tests, `!!x` to make a boolean, deliberate system property reads, `x % 1` on decimals), report nothing, or check a convention.

- A VS Code extension in `editors/vscode` that starts `groovyfmt --lsp` with no setup: formatting of documents and selections (and on save, through VS Code's settings), parse errors and lint violations as you type, quick fixes and fix all (`source.fixAll.groovyfmt`) for `*.groovy`, `*.gvy`, `*.gy`, `*.gsh`, `*.gradle`, `*.jenkinsfile`, `Jenkinsfile` and `Jenkinsfile.*`. It runs `groovyfmt.path`, the workspace's npm package or `groovyfmt` on `PATH`, and otherwise offers to download the matching release, checked against the SHA-256 checksums packaged into the extension when the release was built. An untrusted workspace can't choose the binary. Each release attaches the `.vsix`; publishing to the VS Code Marketplace and Open VSX is set up but off until the repository variables `PUBLISH_VSCODE` and `PUBLISH_OPENVSX` are set.

### Changed

- `max_line_length` wraps long class, interface, trait, enum and record headers, before `extends`, `implements` or `permits` (as few of them as leave the first line fitting) and, when a clause is still too long on its own line, after each comma between its types. The `{` stays at the end of the last line. Groovy's grammar takes a newline at each of these places. On about 62,000 Groovy files from open source projects at `max_line_length = 120`, header lines over the limit drop from 1,339 to 107. What is left is headers inside strings, a single type too long for a line of its own, and long type parameters, which are never broken.
- `docs/releasing.md` describes what the GitHub Action verifies about a download today and how to harden it with immutable releases.

## 0.12.0 (2026-11-13)

### Added

- Seven Jenkinsfile lint rules for what the Declarative Pipeline plugin's parser and validator reject when a build starts, on by default: `JenkinsParallelNesting` (a `parallel` or `matrix` inside another, or `agent` or `tools` on the stage holding one), `JenkinsWhenNesting` (`allOf`, `anyOf` and `not` with the wrong number of conditions or with arguments, and nested conditions under any other condition), `JenkinsMatrixAxes` (a matrix without `axes`, an axis without a valid `name` or `values`, repeated axis names or values, empty `excludes`), `JenkinsInputSection` (a stage `input` without `message`, an unknown or repeated field), `JenkinsEnvironmentEntry` (an `environment` line that isn't `KEY = value`, an invalid or repeated key, a value such as `params.X` that must be quoted), `JenkinsDuplicateOption` (an option or trigger twice) and `JenkinsToolVersion` (a `tools` line without exactly one installation). On the plugin's own test pipelines the Jenkins rules now catch 81 of the 132 invalid ones (49 before); the other 51 need the installed plugins or a running Jenkins to judge. Of its 289 other test pipelines, they report only 6, all of them pipelines its tests expect to fail or tests marked `@Ignore`. They report nothing on the other real pipelines in about 120 open source repositories.
- `GradleRemovedApi`, on by default, for what the Gradle upgrade guides list as removed: the `maven` plugin and `uploadArchives` (7.0), the `findbugs`, `jdepend`, `osgi` and announce plugins (6.0), `configurations.compile` and the other removed configurations (7.0), and an archive task's `archiveName`, `baseName`, `classifier`, `destinationDir`, `appendix` and `extension` (8.0). The message names the version and the replacement. Like `GradleRemovedConfiguration`, it stays quiet when the nearest Gradle wrapper pins a version that still has the construct. In about 120 open source repositories it reports 9 places, all of them builds whose own wrapper no longer has what they use.

### Fixed

- EqualsOverloaded no longer reports a typed `equals(T)` when the class, or a superclass declared in the same file, also declares `equals(Object)`, which can delegate to it, and no longer reports an abstract (bodyless) `equals` declaration. A superclass in another file can't be seen, so a subclass's `equals(T)` there is still reported.
- EqualsAndHashCode no longer reports an abstract class whose `equals(Object)` calls one of its abstract methods (equality, and so `hashCode`, is left to the subclasses), or an `equals(Object)` that is never broader than identity (its body is just `false`, or `this.is(o)` and `o == null` tests joined by `||`), which the inherited `hashCode()` already satisfies.
- EmptyWhileStatement and EmptyForStatement no longer report a loop whose condition does the work with a call, an assignment or an increment, as in `while (in.read() != -1) {}`. `while (true) {}` and `for (x in xs) {}` are still reported.
- The DeadCode documentation no longer reads as if a `break` after a `break` were exempt: only a `break` after a `return` or `throw` (the switch-case habit) is, and a doubled `break` is still reported.

## 0.11.0 (2026-11-13)

### Changed

- `max_line_length` wraps more of the long lines it can. New break points, each where Groovy's grammar reads the code the same with or without the line break:
  - a method's or constructor's parameter list with two or more parameters, one parameter per line (inside `(…)`, where Groovy's lexer drops newlines)
  - an annotation's arguments, and a list in them, when nothing follows the annotation on its line (also inside `(…)` and `[…]`)
  - a call's only argument, or a list's only item, after the opening bracket and before the closing one, when the argument is at least half as wide as what comes before it and then fits on its line (or is an operator expression or a chain that breaks further), only closing brackets, `,` or `;` follow it, and an `=` before it can't break instead; what is inside it then breaks if it must. A list, map or closure as the only argument, or a call ending in arguments that break that way (`f(g(a, b))`, `f(g(h([a, b])))`), breaks inside itself
  - after each comma of a parenthesis-free command call's arguments (`implementation group: 'a',` then `name: 'b'`), when nothing but a comment follows the call on its line and the line up to the first comma then fits (`argumentList : firstArgumentListElement (COMMA nls argumentListElement)*`)

  With `max_line_length = 120`, of the lines over the limit that a break could shorten (leaving out lines inside multi-line strings and comments, lines long only because of a trailing comment, and lines holding a string too long to fit anyway), wrapping now shortens 62% in the corpus (was 46%) and 68% in the trial repositories (was 50%). For every new kind of break, generated cases and a sample of 300 wrapped corpus files parse to the same AST with Groovy 4 before and after wrapping. Without `max_line_length`, output is unchanged.
- Wrapping is faster: it no longer parses the formatted text again before its first pass, or the wrapped text again after its last, since both were already parsed (the same checks run on those parses). On the corpus with `max_line_length = 120`, formatting took 2.4 to 2.5 times the CPU time it takes without wrapping (two measurements, each the mean of two runs); that is now 1.9 to 2.0 times for the same output, and 2.1 to 2.2 times with the new break points above, which wrap more.

## 0.10.0 (2026-11-12)

### Fixed

- A file named on the command line was formatted as Groovy whatever its name, so `groovyfmt *` or `groovyfmt $(git ls-files)` rewrote a Makefile (its recipe tab removed) or a YAML file (its indentation flattened) and exited 0. A named file is now formatted, checked or linted only when a directory search would find it (`*.groovy`, `*.gradle`, `*.gvy`, `*.gy`, `*.gsh`, `Jenkinsfile`), when it is a pipeline named `Jenkinsfile.*` or `*.jenkinsfile`, or when its first line is a `#!` that runs groovy. Any other named file is skipped as `not a Groovy file` (listed under `-v`, failing `--strict`, `"status":"skipped"` in JSON). The new `--force` option reads every named file as Groovy, as before. `--stdin`, `--stdin-filepath` and `--lsp` are unchanged.
- On Linux and macOS, a file rewritten in place between groovyfmt's read and its write (an editor or a file watcher saving it, same inode) was overwritten with the formatted old text. The check before the write compared only the device and inode; it now also compares the size, the modification time and the contents read again, as on Windows, so the newer text stays and the file is reported as `file changed while formatting` (exit 2).
- `--lint` (and `--lsp`) could die of a stack overflow, losing the results for every file in the run, on a Spock `where:` row of tens of thousands of cells or a Jenkinsfile with thousands of nested blocks (`dir { dir { ... } }`, stages in stages, `allOf` in `allOf`). Data table cells are now counted without recursion, and Jenkins blocks nested more than 64 deep are not checked. Lint output on the corpus is unchanged.
- `GradleRemovedConfiguration` reported `compile`, `runtime`, `testCompile` and `testRuntime` in builds pinned to a Gradle that still has them. They were removed in Gradle 7.0, so a script whose nearest `gradle/wrapper/gradle-wrapper.properties` (in its directory or above) has a `distributionUrl` below 7.0 is no longer reported. Across about 90 open source repositories this drops 1,766 of 3,746 reports (all in builds on Gradle 2 to 6); the 1,980 left are under wrappers at 7.0 or later.
- `UnusedImport` reported, and `--lint --fix` deleted, a static import of a getter or setter that the file uses as a property (`import static a.Utils.getAppEnvironment` with `"$appEnvironment"`), which Groovy resolves through that import; removing it broke the build. Such an import now counts as used where the property name appears (40 reports in the trial repositories).
- `UnusedPrivateMethod` and `UnusedPrivateField` reported members that another file uses, which Groovy allows because it doesn't enforce `private`: `it.generateMethods()`, `postProcessingService.getLayerSampleInfo()`, a `@Mixin` class's method called bare, `Constants.DEFAULT_PORT`, a fixture field a spec checks by name. Before reporting, the rules now search the project's other Groovy files for the name (after `.`, `?.`, `.&`, `.@` or `::`, as a whole string, or for a method called bare) in a file that names the member's class and doesn't declare a class of that name itself. The project is the nearest directory with `.git` or a config file, found the same way however groovyfmt is run (`--lint .`, named files, `--changed-since`, the LSP), walked as a directory walk is (exclude patterns honored, no symlinks), and read only when a file has a report of these rules. Past 20,000 files, 256 MiB, or a file over 10 MiB, the two rules report nothing in that project. In the trial repositories this drops 25 of 219 `UnusedPrivateMethod` and 12 of 152 `UnusedPrivateField` reports; in a sample of 19 of them, 18 were used elsewhere and 1 was a same-named class in another package. No other report changes.
- `UnusedVariable` no longer reports Spock's `IOException e = thrown()`, where the declared type is the exception expected and removing the variable changes the test (50 reports), or a variable named `ignore` or `ignored`, which is unused on purpose (3 reports).
- The GitHub Action, with no `version` input, failed with only `release not found` when the version in its ref's `Cargo.toml` has no release (`@v0.9.0`, whose release run failed, or `@main` after a version bump and before its release). It still fails there rather than install a release the ref didn't name, but the error now names the missing release and says to use a release tag or `version: latest`. The README no longer says `main` installs the latest release, and the CI `action` job now runs the action from a ref at the latest release and from one with no release. The Gradle plugin's message for a missing release (HTTP 404) no longer says the repository is private; it says the release may not exist and how to pick one.

### Changed

- The README is now a short front page: what groovyfmt is, why it is safe to run, install, quick start, and a few lines per topic. The reference material moved, unchanged in substance, to `docs/`: `usage.md` (command line), `formatting.md`, `configuration.md`, `lint.md`, `output-formats.md`, `ci.md`, `editors.md`, `agents.md`, `windows.md` and `coverage.md`. The README now lists `cargo install groovyfmt` (0.9.2 is on crates.io), drops the stale private-repository note for pre-commit, updates the pipeline-library lint example to today's output, and dates the npm-groovy-lint benchmark to the build that had 14 rules on by default (today 46 are). `--help` points at `docs/output-formats.md` for the JSON schema.

## 0.9.2 (2026-11-12)

### Fixed

- `normalize_spacing` could leave a file that a second run changed again. A line whose respacing would have moved an aligned `=`, `:` or comment was held as written, judged against how its neighbors were written, and stayed held after those neighbors changed and the reason was gone; a second run, starting from the new text, respaced it. Found on a Grails `application.groovy` (streamaserver/streama). Every decision to keep spacing is now made from the current text of the line and its neighbors and checked again on each pass, so the output is a fixed point by construction. A new test edits formatted output (a space deleted, a space added before `:` or `=`, a trailing `;` removed, a line deleted) and requires one more run to settle; over the corpus and the trial repositories (48,033 files), with `normalize_spacing`, with `max_line_length = 120`, with both, and after `--lint --fix` at every combination of the two, no file fails it (0.9.1: 1 file in each set with `normalize_spacing`).
- A file whose write failed (read-only, held open by another program on Windows, a directory that can't be written, a file changed while formatting) was still counted in `reformatted N of M files`. It is now only an error: exit 2, `"status":"error"` with the reason in JSON, and not counted as reformatted or fixed.
- The test suite's timing checks measured on fast machines against a 50 ms floor, under which a quadratic slowdown could pass. They now grow the input (or, at a hard input limit, repeat the call) until a run costs 100 ms, and the wrapping test that compared elapsed time with 60 s uses the same check. No change to groovyfmt's behavior.

### Changed

- With `normalize_spacing`, a single space before the `:` of a map key or named argument stays only when a nearby line has the `:` of a key of a different length in the same column (`9 :` over `10:`). Keys of the same length that happen to line up (`access :` over `access :`) now lose the space, so rows of one map no longer come out half with `access :` and half with `access:`.
- With `normalize_spacing`, a run of spaces before a trailing comment absorbs a change earlier on its line only when the comment lines up with something on a nearby line that stays where it is. When the lines around it change the same way, the comment now moves with them and stays in their column, instead of staying put while theirs move.
- Together, on the 23,766-file corpus with `normalize_spacing` on: `unchanged=13068 formatted=10613 lines_changed=602095` (0.9.1: 602,094); over the corpus and the trial repositories (48,046 files), 577 lines in 146 files come out differently from 0.9.1. With the option off, output is unchanged.

- The grammar pin moves to tree-sitter-groovy 9129e32. Newly accepted: several divisions inside GString interpolations on one line (`"${a/1000f},${b/1000f}"`); a slashy string starting with `=` (`split(/=/, 2)`); an empty map as an index (`render [:] as JSON`, which Groovy reads as `render[:]`); command calls on a safe-navigation or spread-dot receiver with a positional first argument or as a value (`resolver?.setLocale request, response, l`, `def saved = [a, b]*.save flush: true`), with a ternary first argument (`menuIcon ext == 'pdf' ? A : B, m`), and on a dotted receiver as a call's first argument (`form(new Spec().ui new Attachment(), { })`, where the command takes the rest of the arguments); `final` before a parameter annotation; and files with classic Mac line endings (a lone CR), whose line comments now end at the CR and which keep their CR line endings when formatted. A `/` right after an operand on its line is now always division, as in Groovy, so `x = a/2 + b/2` no longer reads `/2 + b/` as a slashy string. On the 23,766-file corpus nothing changes (85 skipped, same output); across five trial directories of 38,413 files, skipped files go from 265 to 253 and no file that parsed before fails now.

## 0.9.0 (2026-11-10)

### Added

- `max_line_length` config option (40 to 400, no default): wrap lines longer than that many columns where a line break is safe in Groovy. It only adds line breaks: an argument list, list literal or map literal with two or more items breaks one item per line (inside brackets, where Groovy's lexer drops newlines), a chain of three or more calls breaks before each `.` but the first, a binary expression after each `||`, `&&`, `==`, `!=`, `+` or `-` of its lowest-precedence level, a ternary after `?` and `:`, `?:` after itself, and as a last resort an assignment after `=`. Operators always end the line. It never breaks inside a parenthesis-free command call, a closure or block written on one line, an annotation, an `import`, a `case` label, a Spock `where:` block or a string, and never joins lines. Each pass must parse to the same tree as the input, and the result must keep every token and the tree shape, or the file is formatted without wrapping. With `max_line_length = 120`, over the 23,766-file corpus and the files of 81 trial repository directories (46,014 files in all), it wraps 8,715 files and brings the lines over 120 columns from 89,754 to 58,989; the rest are mostly lines inside strings and comments, strings too long to fit, trailing comments, and lines with no break this allows. Formatting twice changes nothing, no file is newly skipped and none falls back to formatting without wrapping, at 100 and 120 columns with and without `normalize_spacing`. On a sample of 3,000 wrapped files, Groovy 4.0.33's own parser accepts the wrapped text whenever it accepts the original, with the same parse tree and the same AST. `-v` lists files formatted without wrapping and why, and `--suggest-style` ignores the key. Without the key, output is unchanged.
- Windows x86_64: each release gets `groovyfmt-<tag>-x86_64-pc-windows-gnu.zip`, a single `groovyfmt.exe` that needs only Windows' own DLLs, with its `.sha256`. It is cross-compiled on Linux with mingw-w64 and tested on Windows Server 2022 (the whole test suite, NTFS write behavior, shells, a corpus sample) and under Wine (the whole test suite and corpus). Output matches Linux and macOS byte for byte: paths print with `/` in every format and patch, and line endings are never translated. Formatting in place stays a rename of a temporary file; what differs there (hard links, file permissions, how a changed file is detected) is in the README's Windows section. The GitHub Action, the npm packages (`@groovyfmt/win32-x64`) and the Gradle plugin install it on Windows x64. `scripts/ci-local.sh` builds it and runs the tests under Wine when mingw-w64 and Wine are installed.
- `--lsp`: a Language Server Protocol server on stdin and stdout for editors and coding agents. It formats documents and selections (as `--stdin --stdin-filepath` and `--lines` would, `normalize_spacing` included), publishes parse errors and lint violations (as `--syntax` and `--lint`), and offers the `--lint --fix` fixes as code actions (`source.fixAll.groovyfmt` and a quick fix per violation). Each document uses the config for its path, read again on every request, and `exclude` applies. Positions are UTF-16, or UTF-8 when the client offers it. Setup for Neovim, VS Code, Helix and Zed is in the README.
- pre-commit hooks in the repository (`repo: https://github.com/costajohnt/groovyfmt`): `groovyfmt`, `groovyfmt-check` and `groovyfmt-lint` run the binary on `PATH`, and `groovyfmt-source`, `groovyfmt-check-source` and `groovyfmt-lint-source` build it from source with cargo.
- A GitHub Action (`uses: costajohnt/groovyfmt@<ref>`): installs the release binary for the runner (Linux or macOS, x64 or arm64) after checking its `.sha256`, puts it on `PATH`, and runs it with `args` (default `--check --output-format github`).
- Packaging for npm (`npm/`, the `groovyfmt` package with one `@groovyfmt/<os>-<arch>` package per platform), Homebrew (`packaging/homebrew/`, a formula rendered from a release's checksums) and a Docker image (`Dockerfile`, `scratch` plus the static binary). None of these is published yet: the release workflow's `publish-npm` and `publish-image` jobs stay off until the repository variables `PUBLISH_NPM` and `PUBLISH_IMAGE` are set (`docs/releasing.md`). CI builds and runs each against the latest release.
- `--strict`: with `--check`, `--lint` or when formatting in place, list the files that were skipped (they don't parse, aren't UTF-8, are over 10 MB or nest too deeply) and exit 1 if there are any. Without it a skipped file never affects the exit status, so CI can pass on files nothing checked.
- `--` ends the options: every argument after it is a path, even one starting with `-`.
- `--syntax` only parses, and reports each place groovyfmt could not parse as `path:line:col: could not parse: <message>` (up to 10 per file, then a count of the rest), exiting 1 if any file doesn't parse. The message names a bracket left open, or quotes the text the grammar stopped at and where it was. `-v` and `--strict` print the same lines under each file skipped for a parse error, and `--stdin` prints them after its error.
- `--output-format json` for `--check`, `--lint`, `--syntax` and formatting in place: one JSON document on stdout with each file's status, skip reason and diagnostics (with end positions) and a summary, in a versioned schema documented in the README. `--output-format sarif` for `--lint` and `--syntax`: a SARIF 2.1.0 log for GitHub code scanning. File names and quoted source are escaped so they can't act as terminal escapes or workflow commands.
- `--lint --fix` removes unused and duplicate import lines and unnecessary semicolons in place, then reports what remains (exit 1 if anything does). Each fix is checked as formatting is: the result must parse cleanly, keep every other token and the shape of the parse tree, and lint with no new violations, or the file is left untouched and listed as `not fixed`. Files that don't parse are never fixed; writes follow the same symlink, owner, hard-link and `exclude` rules as formatting.
- `--diff` with `--check` (and `--lint --fix`): print a unified diff of the changes instead of the file names, writing nothing, for `git apply` or `patch -p1`. A file whose name or diff would print a control character, `##[` or a line starting `::` gets a `# groovyfmt: ... diff not shown` line instead.
- `--lines <start>-<end>` (repeatable) for one file or `--stdin`: change only those lines; every other line stays byte for byte, and the result passes the same token check as formatting.
- `--changed-since <rev>`: limit a run to the files that differ from a git revision, plus untracked files, under the working directory.
- `--explain <Rule>`: a rule's description, why it matters, flagged code and a fixed version, whether `--lint --fix` fixes it, whether it is on for the current directory, and the config lines to turn it off or on. `--rules` is unchanged.
- README: "Using groovyfmt with coding agents", with a Claude Code PostToolUse hook that formats and lints each Groovy file Claude edits and reports problems back to it, and an `AGENTS.md` / `CLAUDE.md` snippet.
- A Gradle plugin (`gradle-plugin/`, id `io.github.costajohnt.groovyfmt`) with `groovyfmtCheck` and `groovyfmtLint`, which `check` runs, and `groovyfmtFormat`. It downloads the release binary into `~/.gradle/groovyfmt/`, checks its `.sha256` before unpacking it, and reuses it; `binary` runs a local one instead. Gradle 7.6+ on Java 11+, configuration cache compatible. Not published yet: use it with `includeBuild` from a checkout (README, Gradle). The release workflow's `publish-gradle-plugin` job stays off until the repository variable `PUBLISH_GRADLE_PLUGIN` is set (`docs/releasing.md`).
- `normalize_spacing` config option (off by default): also fix the spaces between tokens within a line, in a conventional Groovy and Java style (one space around binary operators and after commas, `if (`, `foo(x)`, `[a: 1]`, `{ x }`, no space inside parentheses and brackets). It never moves a line break and never touches strings or comments. Alignment is kept: a run of spaces stays when the next token lines up with one on a nearby line, a line whose changes would move an aligned `=`, `:` or comment out of its column is left as it is up to that column, and Spock `where:` blocks are left exactly as written, as is spacing that could change how Groovy reads the code (`a -b`, `foo (x).bar()`, `a [1]`). The output must parse to the same tree shape as the input, or the file is formatted without spacing changes. On the 23,766-file corpus it changes 35,666 more lines in 4,455 files than formatting without it; formatting twice changes nothing, and no file is skipped that isn't skipped without it. Lines over 1,000 bytes keep their spacing, and a file whose alignment passes don't settle is skipped. With the option off, output is unchanged.

- Lint rules for declarative Jenkinsfiles, Gradle build scripts and Spock specs, for the structural mistakes those tools otherwise report only when a build runs (README, Lint rules). Jenkins: `JenkinsMissingSection`, `JenkinsConflictingSections`, `JenkinsUnknownSection`, `JenkinsStatementOutsideSection`, `JenkinsScriptRequired`, `JenkinsUnknownWhenCondition`, `JenkinsMisplacedOption`, `JenkinsDuplicateStageName`, `JenkinsStageName` and `JenkinsAgentForm`, checked on a top-level `pipeline { }` in `Jenkinsfile`, `Jenkinsfile.*`, `*.jenkinsfile` or any file that starts with one. Gradle (`*.gradle`): `GradleRemovedConfiguration`, `GradleJcenter`, `GradleLeftShiftTask` and `GradleDynamicVersion` (off by default). Spock: `SpockBlockOrder`, `SpockDataTableColumns` and `SpockEmptyBlock` (off by default). On the pipeline-model-definition plugin's own test pipelines the Jenkins rules report nothing on the 283 valid ones and catch 49 of the 132 invalid ones (49 of the 55 whose error is the kind these rules look for; the rest are step parameter, environment value and matrix axis errors, which need the installed plugins to judge). They report no false positives on about 300 other real pipelines, and the Spock rules that are on by default report nothing on Spock's own specs.
- 25 more general lint rules, named after their CodeNarc equivalents and chosen by how often 30 real CodeNarc configurations enable them, kept to what the syntax tree decides without type information (README, Lint rules). On by default: `UnnecessaryGroovyImport`, `ImportFromSamePackage`, `DeadCode`, `EqualsAndHashCode`, `EqualsOverloaded`, `ObjectOverrideMisspelledMethodName`, `ReturnFromFinallyBlock`, `EmptySwitchStatement`, `EmptyStaticInitializer`, `EmptyInstanceInitializer`, `BrokenNullCheck`, `RemoveAllOnSelf`, `MissingNewInThrowStatement`, `ExceptionNotThrown`, `UnusedPrivateField`, `UnusedPrivateMethod` and `UnusedVariable`. Off by default, because on real code they found almost only things written that way on purpose: `ThrowExceptionFromFinallyBlock`, `AssertWithinFinallyBlock`, `ToStringReturnsNull`, `DuplicateSetValue`, `ConstantTernaryExpression`, `ConstantAssertExpression`, `ComparisonOfTwoConstants` and `BrokenOddnessCheck`. Each was checked against CodeNarc's own test cases for it and on the 23,766-file corpus and 78 trial repository directories; the README says where groovyfmt deliberately reports less than CodeNarc. On the corpus a default `--lint` goes from 3,767 to 4,893 reports.

- Suppressing lint reports from the source: `// groovyfmt-ignore [Rule, ...]` for its own line (after code) or the next line (alone), `// groovyfmt-ignore-start [Rule, ...]` to `// groovyfmt-ignore-end`, and CodeNarc's own `codenarc-disable` / `codenarc-enable` / `codenarc-disable-line` comments and `@SuppressWarnings('Rule')` / `@SuppressWarnings(['A', 'B'])` (with `'all'` and `'CodeNarc'`) on a declaration or import, so projects moving from CodeNarc keep their suppressions. Suppressed reports are left out of every output, the exit status, `--lint --fix` and the language server. `UnusedSuppression` (off by default) reports a suppression that matches nothing.
- `// groovyfmt: off` to `// groovyfmt: on` keeps those lines exactly as they are when formatting; the rest of such a file is formatted as with `--lines`.
- A lint baseline: `--lint --write-baseline[=FILE]` records the current violations (default `.groovyfmt-baseline.json`), and `baseline = "..."` in the config or `--baseline FILE` makes `--lint` report only the ones it doesn't hold, exit 0 when nothing else is left, and count stale entries (failing with `--strict`). Entries are keyed by path, rule, a fingerprint of the line's text and an occurrence index, never a line number, so unrelated edits don't disturb them. `--lint --fix` and the language server leave baselined violations alone. A config's `baseline` must stay inside the config's directory (no `..`, not absolute, not through a symlink leading out); the file is read with the same limits as sources.

### Changed

- `--lint --fix` also removes an `ImportFromSamePackage` import line (not when the file declares a class of the same name). `UnnecessaryGroovyImport` is reported but never removed: the import can be what beats a class of the same name in the package, which one file can't show.
- `--lint` text output ends each violation `--lint --fix` would fix with ` (fixable)` (`UnusedImport`, `DuplicateImport` and `UnnecessarySemicolon`; an import sharing its line with anything but a `;` isn't fixable). The `github` format is unchanged.
- The grammar is vendored: its generated C sources live in `grammar/` (from the tree-sitter-groovy fork at the same commit as before, `65a9b34`) and `build.rs` compiles them, replacing the git dependency on the fork. groovyfmt now builds from this repository alone, so `cargo install --locked --git` fetches one repository and the crate can be packaged for crates.io. Output is unchanged: formatting and `--lint` give byte-identical results on the 23,766-file corpus and 78 trial repositories. `scripts/update-grammar.sh` updates `grammar/` from a grammar checkout.
- The grammar pin moves to a newer `groovyfmt-base` of the tree-sitter-groovy fork. Files skipped for a parse error go from 117 to 85 on the 23,766-file corpus, from 21 to 15 across the 13 repositories, from 26 to 23 across the 21 more, and from 48 to 6 across 41 more repositories (5,029 files). Newly accepted: `def` before a class or interface (`def class X`, `def static class X`), `def final x = 1` and `def Object x` parameters; `new`, `switch`, `in` and `static` where they are names (`[switch: 'on']`, `in.property`, `static.unused = { }`, `yield()`); a comparison right after a name where type arguments could start (`if ((value>0)&&(value<99))`, `i<n ? a : b`); slashy strings with `\\/` (`~/:\\/\\/.+/`); quoted command names (`'x:title' lang: 'en', 'text'`, `'CatchThrowable' priority: 1`); a call chained onto a call (`a(x) or(b(y))`, `(page.list 0 isEmpty())`); `assertEquals (-1), x`, `visibilityOf(el modalBy)` and `def api = toApi 'A': src`; Groovy 5 and 6 forms (`for await`, `for (int i, v in list)`, `case Integer i when i > 0 ->`, `??`, `??=`); spaced and annotated type arguments (`(List <T>) x`, `Closure <V> v)`, `Arrays. < T > asList(a)`, `String @A []`, `implements @A I`); nested array initializers and `@Target({A, B})`; script variables with modifiers (`public static final long X = 1`), `Object a = f(), b`, `def (head, *tail) = l`, `(1..5)[*1..3]`, `[][]`; `assert` and labels inside `${}`; files starting with two byte order marks; `x .42`; and `else` is now always a keyword, so `if (a) a b` followed by `else` on the next line keeps its `else`.
- Each thread reuses one parser instead of creating one per parse (two to four per file): about 2% less CPU time on the 23,766-file corpus (`--stats`, 44.4 s user against 45.2 s, mean of 5 runs each).

### Fixed

- `UnusedImport` no longer reports an annotated import (`@Library('lib') import x`, `@Grab('g:a:v') import y`): the import is there to carry the annotation, which loads the library. A duplicate annotated import is still reported but not fixable. Across the corpus and the 78 trial repository directories this removes 1 report.
- `UnnecessarySemicolon` no longer reports a `;` before a line starting with `++` or `--`: without it, `a[0]` then `++n` reads as `a[0]++` then `n` (bigtop `TestBlockRecovery`). This removes 1 report across the same code.
- A body's `{` on a line of its own (`void f()` then `{`, the Allman style) lines up with its declaration or statement, as its `}` and its first statement already did, instead of being indented as a continuation. Of the files that parsed cleanly before, 657 across the corpus and the 75 repositories change, every changed line one of those `{` lines moving out one step.
- A line starting with a map key or named argument called `else`, `catch` or `finally` (`[` then `else: 1,`) keeps its indent instead of moving to the level of the line holding the `[` or `(`. Across the corpus and the 34 trial repositories no file has that shape; one GPars file changes because the grammar reads its `else` (after `if (follower) follower value`) as a name, and that `else` block now lines up with its `if` instead of sitting one level left of it.
- Formatting a file whose name is close to the 255-byte limit no longer fails with `File name too long`: the temporary file beside it now has a short name of its own instead of one built from the file's name.
- A worker thread that dies outside the per-file panic guard now turns each of its files into an `internal error, please report` error. Before, its results were dropped, the list came back short and later results could be reported against the wrong files.
- Command-line parsing: a flag that takes no value rejects one (`--check=false` used to turn check on), and `--stdin` with path arguments is an error instead of ignoring the paths (name the buffer with `--stdin-filepath`).
- `UnusedImport` no longer reports a class used only inside `${...}` that the grammar leaves as plain string text, as in a `"""` string holding `"${TextUtil.escapeString(path)}"` (common in Gradle's integration tests). Across the corpus and the 34 repositories this removes 97 false reports.
- `UnusedImport` checks comments for the name as a whole word, so `// Listing` no longer counts as a use of `List`. This adds 29 reports across the corpus and the 34 repositories, each an import whose name appears nowhere else as a word (`import org.gradle.api.Project` next to `ProjectBuilder`). Comment text used to be searched once per import, which took 10 s on a 5 MB file with 30,000 imports; it now takes under 1 s.
- `UnnecessarySemicolon` no longer reports a `;` before a line starting with `{`: without it the closure on that line becomes an argument of the statement before (`new DataflowVariable();` then `{-> ... }.callTimeoutAsync(t)` in GPars).
- `AssignmentInConditional` treats an assignment in extra parentheses, `if ((m = matcher(s)))`, as meant, as GCC and ESLint do.
- `ComparisonWithSelf` (off by default) no longer reports a comparison inside a GORM where query (`Book.where { title == title }`, `@Where({ ... })`), where the left side is the domain property and the right a variable.
- `DuplicateCaseStatement` treats `case 'a':` and `case "a":` as the same label, as `DuplicateMapKey` already did for keys.

## 0.5.0 (2026-11-10)

Most of this release comes from a second full audit (`docs/audit-2026-11-09-full.md`). groovyfmt runs in CI on pull-request content, so these matter:

### Security

- File names and lint messages can no longer inject the older `##[command]` GitHub Actions workflow syntax, which the runner accepts anywhere in a line (`##[add-mask]`, `##[stop-commands]`, `##[error]`). Every printed path, message and panic report shows `##[` as `##\[`.
- A symlink named on the command line stays a symlink: the file it points to is formatted, through any chain of links, and reports name the link as typed. Before, the link was replaced by a formatted regular file and its target left untouched. A link whose target matches `exclude` is skipped, and in write mode a named link, to a file or a directory, whose target is outside the working directory is an error (exit 2) and nothing is rewritten through it, so `groovyfmt *` in an untrusted checkout can't write through a committed link to files elsewhere; `--check` and `--lint` still read such a link. Arguments that are not themselves links, such as `../other-project`, are unaffected.
- A file is only written if its path still names the file that was read. If it was replaced by another file or a symlink in between, the write fails with `file changed while formatting` (exit 2) and nothing is written; before, the rename replaced whatever was at the path. Edits made to the same file in between are not detected.
- Formatting a run of indented comments was cubic in its length (4,000 lines took over two minutes) and long blocks were superlinear. The indent pass now moves one tree cursor forward through the file instead of looking up each line's node, parents and previous siblings from the root: 4,000 comment lines take 0.01 s, and an 800,000-line file 5.7 s instead of 30 s.
- In-place formatting and `--check` no longer hold every changed file's new text in memory until the run ends. Each worker writes the file, or for `--check` only notes that it changed, as soon as it is formatted.

### Added

- `--stdin-filepath <path>` (with `--stdin`): find the config file by walking up from that path's directory, as if formatting the file on disk, and use the path as the name in error messages and `--output-format github` annotations. The file need not exist. If the path matches `exclude`, stdin is written back unchanged and the exit status is 0.
- `exclude = [...]` config option: glob patterns, relative to the config file's directory, for files and directories to skip on top of the built-in list. `*` and `?` match within a path segment, `**` across segments. Excluded directories are not descended into, and excludes also apply to files named on the command line.

### Changed

- Each file is now governed by the nearest `.groovyfmt.toml` / `groovyfmt.toml` above the file itself, not the one above the working directory. `groovyfmt --check ../proj` used to apply the working directory's config (or the defaults) to `proj` and report files formatted under `proj`'s own config as needing changes, and write mode re-indented them; a subproject with its own config was formatted by the root's config when run from the root. A nested config replaces its parent's entirely, nothing is merged. Its `exclude` and `[lint]` settings apply inside its directory, and the parent's `exclude` still decides whether that directory is searched (a config inside an excluded directory is never read). That parent exclusion also covers files named on the command line, `--stdin-filepath`, and runs started inside the excluded directory, which used to see only the nested config; `--config` overrides it. A file outside the working directory no longer picks up the working directory's config. `--config` still applies one file to everything and `--indent` still overrides the indent; `--rules` and `--stdin` without `--stdin-filepath` still use the working directory's config. A config file that fails to parse stops the run (exit 2) only when a file or directory it governs is reached. `-v` prints one `config:` line per config in use. (M5)
- The Linux arm64 release binary is now a static musl build, like the x86_64 one, so it runs without glibc (Alpine, Amazon Linux 2, RHEL 8, Debian 11, Ubuntu 20.04). Its asset is now named `groovyfmt-<tag>-aarch64-unknown-linux-musl.tar.gz` instead of `...-aarch64-unknown-linux-gnu.tar.gz`.
- The minimum supported Rust version is 1.90 (`rust-version` said 1.85, which can't build the tree-sitter dependencies). CI now runs the tests on 1.90.0.
- A release tag now publishes only if it matches the Cargo.toml version, is on `main`, has a CHANGELOG heading, and fmt, clippy, the tests and a build and smoke test of every release binary pass on the tagged commit. All four release targets are also built and run on every pull request.

### Fixed

- UnusedImport no longer reports a class used only through a brace-less GString interpolation such as `"$Name"` or `"$Name.CONST"`; removing the import as advised broke the code.
- Formatting a file in place keeps its owner and group (root formatting a bind-mounted checkout used to leave every changed file owned by root) and keeps its hard links: a file with more than one link, or whose owner can't be kept, is overwritten in place instead of replaced by a renamed temporary file.
- A file named more than once, directly or through overlapping arguments (`groovyfmt . src`, `A.groovy ./A.groovy`, `sub/../A.groovy`), is formatted and reported once. Each in-place write uses its own temporary file name, and a failed write no longer deletes a file that already had that name.

## 0.4.0 (2026-11-09)

From a full audit (`docs/audit-2026-11-09.md`). groovyfmt runs in CI on pull-request content, so these matter:

### Security

- Symlinks inside searched directories are no longer followed. A link cycle used to hang the run, and a link out of the tree could make groovyfmt read or rewrite files elsewhere.
- A file name starting with `::` can no longer inject a GitHub Actions workflow command into the log.
- Deeply nested input no longer crashes `--lint` with a stack overflow, and no longer makes the formatter's output grow quadratically.
- FIFOs, device files and files over 10 MB are skipped.
- In-place writes are atomic (temporary file plus rename, permissions kept), so a crash can't leave a truncated file, and a file swapped for a symlink mid-run is replaced rather than written through. Read-only files are left alone.

### Added

- `continuation_indent` config option: the indent for arguments, list and map literals, and continued lines, separate from block indentation. Set it to 8 for IntelliJ-formatted code.

### Parsing

- A `[` that starts a new line begins a list or map instead of subscripting the line above, so Grails controller actions ending in `[model: value]` parse. Also `final` method parameters, traits with `implements`, and subscripts as later arguments of parenthesis-free calls. Corpus coverage 85.6% to 88.1%; OpenBoxes (a Grails app outside the corpus) 88% to 95.6%.

### Fixed

- `indent_after_labels` was cubic in block length (221 s for a 20,000-line block, now 0.24 s), and treated any label, not just Spock's, as opening a block.
- Mixed line endings are kept per line instead of converting the whole file to CRLF.
- Lint columns count characters, not bytes, so annotations land in the right place after non-ASCII text.
- A crash while processing one file is reported as an error for that file (exit 2) instead of aborting the run; `| head` no longer panics; unreadable directories exit 2.
- The formatter's safety check now compares string fragments exactly, closing a blind spot for whitespace before `${…}` inside GStrings.
